## 1. 公開までの初期設定（一度だけ）

### GitHub Pages で公開する

```bash
cd gadget-signal
git init && git branch -M main
git add . && git commit -m "init: Gadget Signal"
gh repo create <あなたのアカウント>/gadget-signal --public --source=. --push
```

1. GitHub のリポジトリ → **Settings → Pages → Build and deployment → Source を「GitHub Actions」に変更**
2. `config/site.yaml` の `base_url` を実際のURLに書き換える
   例: `https://<アカウント名>.github.io/gadget-signal`
3. `git push` すると `deploy.yml` が走って公開される

### 独自ドメインにする場合

1. `config/site.yaml` の `base_url` をそのドメインに変更
2. `scripts/build.py` の出力に `public/CNAME` を追加する（1行、ドメイン名のみ）
3. DNS で `A` レコードを GitHub Pages のIPに、または `CNAME` を `<アカウント>.github.io` に向ける
4. Settings → Pages → Custom domain に入力し、Enforce HTTPS を有効化

独自ドメインは検索評価が自分に貯まるので、**本気でやるなら最初から取ったほうがいい**（後から移すと初期の評価を捨てることになる）。

### 検索エンジンへの登録

- Google Search Console にプロパティを追加 → `sitemap.xml` を送信

### アクセス解析（Cloudflare Web Analytics）

`config/site.yaml` の `cf_analytics_token` にトークンを入れると、全ページの `<head>` に
ビーコンのスクリプトが入る。**Cookie を使わないので同意表示は不要。**
空文字のあいだはタグを一切出さないので、外部スクリプトも読み込まない。

レポートは https://dash.cloudflare.com/ → Analytics → Web analytics で見る。

**設定方法に注意点がある。** `gadgetterminal.com` は Cloudflare で DNS だけを管理し、
通信は GitHub Pages に直接届く構成（グレー雲）。このため Cloudflare が提示してくる
「自動セットアップ」は**機能しない**（プロキシを通過しない通信にはビーコンを注入できないため）。

サイト追加時にホスト名を入力したら、候補の**下段**にある
「Click here to use "gadgetterminal.com" which does not belong to Cloudflare websites」
を選ぶこと。これで JS スニペット方式になり、トークンが発行される。

計測を止めたいときは `cf_analytics_token` を空に戻して再ビルドすれば、タグごと消える。

### GA4 を併用する場合

`analytics_id` に測定ID（`G-` で始まる）を入れれば、Cloudflare と併用できる。

ただし `analytics.google.com` は広告ブロック系の遮断リストに載っており、
**開発環境のネットワークからは管理画面を開けない**（DNS が経路上で書き換えられている）。
Chrome のセキュア DNS を有効にすれば開けるが、常用は勧めない。
- 最初の 2〜3 週間はインデックスされない。焦らない

## 2. 定時実行

収集と記事生成は **毎朝1回**。**1日3本**を、まとめて1回で公開する。

| JST | 動くもの | 内容 |
|---|---|---|
| 05:30 | `collect.yml` | 収集 |
| 06:00 | `daily-article.yml` | 記事3本 → ビルド → 公開 |
| 〜06:30 | — | サイトに反映 |

### なぜ朝6時なのか

**海外ガジェットのニュースは米国の営業時間に出る。** 日本時間でいうと深夜〜早朝。05:30 に収集すると米国の丸1日ぶんが拾えるので、その日いちばん新しい状態で書ける。日本の他媒体が朝に拾い上げるのとほぼ同時に出せる。

公開が 06:30 頃になるので、**通勤時間帯（7〜9時）には読める状態**になっている。

生成は本人の Claude 利用枠を消費するが、就寝中に終わるので日中のローカル作業と5時間ウィンドウを取り合わない。

### 本数を増やさない

新規ドメインで記事を大量に積むと、Google の「スケーリングされたコンテンツの不正使用」ポリシーの形に見える。**判定基準は量ではなく「価値を足しているか」**なので、本数ではなく1本ごとの固有価値（日本の法規制・入手性・代替品）で勝負する方針にしてある。

**公開時刻を分散させることは検討したが、やめた。** Google は投稿時刻の分散を評価しないため効果が無く、`draft` + 予約公開の仕組みを維持するコストに見合わない。

記事生成は `claude_code_oauth_token` を使うため **Claude サブスクリプションの利用枠を消費する**（GitHub Actions の実行時間自体は public リポジトリなので無料）。
日中の作業と5時間ウィンドウを取り合わないよう、意図的に夜に寄せてある。時刻を変えるときはこの点を考慮すること。
手元で回すなら:

```bash
python3 scripts/collect.py --top 30
```

時刻を変える場合は cron を UTC で書く（JST = UTC+9）。

| やりたい時刻(JST) | cron (UTC) |
|---|---|
| 07:00 | `0 22 * * *` |
| 05:30 | `30 20 * * *` |
| 06:00 | `0 21 * * *` |
| 22:30 | `30 13 * * *` |
| 23:00 | `0 14 * * *` |
| 09:00 | `0 0 * * *` |
| 07:00 と 19:00 | `0 22,10 * * *` |

### ネタを指定して書かせる

自動選定に任せず、こちらから製品を指定する経路が2つある。

**(A) キューに積む — 通常はこちら**

`data/queue.md` の `## 未処理` に URL を1行足しておく。

```
- https://www.kickstarter.com/projects/xxxx/yyyy
- https://example.com/product  日本での入手性を厚めに
```

毎朝の定期実行が、ダイジェストより先に**ここを上から最大3本まで消化する**。
書き終えた行は同じコミットで `## 処理済み` に移動する。記事にできなかった行は
理由付きで `## 保留` に移る（黙って消さない）。積みすぎても消えず、次の実行に持ち越される。

URL の後ろに書いた文字列は切り口の注文として読まれる。

スマホの GitHub アプリからも編集できるので、思いついたときに放り込める。

**(B) その場で書かせる**

Actions タブ →「毎朝の記事下書きを作って公開」→ Run workflow →
`url` 欄に URL を貼る（複数はカンマ区切り）。

この場合は**指定した URL だけ**が記事になる。3本に水増ししない。
`url` を空のまま実行すれば、従来どおり自分でネタを探す。

> **利用枠に注意。** (B) は Claude の利用枠を即座に消費する。日中にローカルで
> 作業しているときに走らせると、5時間ウィンドウを取り合う。急ぎでなければ
> (A) に積んで次の定期実行に回すほうが安全。

## 3. よくあるトラブル

### 特定のソースだけ 0 件になる

```
! techpowerup: 0件 (status=403)
```

多くは User-Agent 拒否。`config/feeds.yaml` の `defaults.user_agent` を実在ブラウザ相当の文字列に変えると通ることが多い。
それでも駄目なら、そのソースに `enabled: false` を付けて外す。**1ソースが死んでも全体は止まらない設計になっている。**

### 同じ記事が何度も候補に出る

`data/seen.json` が消えている可能性がある。GitHub Actions で回している場合は、コミットが成功しているか確認する。

### 記事が公開されない

- `draft: true` が残っていないか
- front matter の `---` が先頭行にあるか（前に空行があるとパースに失敗する）
- ビルドログに `! front matter がありません` が出ていないか

### クラスタリングが効きすぎて別の話題がまとまる

`scripts/collect.py` の `cluster()` にある閾値 `0.55` / `overlap >= 3` を上げる。

## 4. 育て方のロードマップ

| 時期 | やること | 判断基準 |
|---|---|---|
| 〜1か月 | 記事30本。ソースを10→20に増やす | 毎日1本以上出せているか |
| 2〜3か月 | Search Console で流入キーワードを見る。伸びたテーマのまとめ記事を作る | 検索表示回数が動き出したか |
| 3か月〜 | 収益化を検討（`site.yaml` の `affiliate.enabled`）。X連携で初速をつける | 月間PVが4桁に乗ったか |
| 6か月〜 | 実機レビュー（現物購入）を混ぜる。一次コンテンツが最大の差別化 | 指名検索が発生しているか |

### 収益化を入れるとき（もしもアフィリエイト）

**仕組みは実装済み。提携が通ったら設定を入れるだけ。**

1. もしもアフィリエイトに登録し、サイトを追加して Amazon などと提携する
2. 管理画面で発行されたリンクをコピーし、**商品URLの部分を `{url}` に置き換える**
3. `config/site.yaml` に貼って `enabled: true` にする

```yaml
affiliate:
  enabled: true
  moshimo_amazon: "https://af.moshimo.com/af/c/click?a_id=0000000&p_id=170&pc_id=185&pl_id=4062&url={url}"
```

`enabled: false` のあいだは代替品セクションは出るがリンクは素のURLのままで、広告表示も出ない。
提携先ごとにリンク形式が違うため、`moshimo_rakuten` / `moshimo_yahoo` も同じ要領で設定する。

**Amazon アソシエイト直ではなく、もしも経由にしている理由:**
直契約は審査が厳しく、承認後に一定期間内の適格販売が必要になる。アクセスが立ち上がる前に
申し込むとその条件を満たせない恐れがあるため、まずは審査の通りやすいもしもで始める。

### X への自動投稿

公開が終わると `deploy.yml` の `notify` ジョブが `scripts/xpost.py` を実行し、
その日の記事を X に投稿する。**認証情報が未設定なら何もせず終了する**ので、
設定するまでは無効のまま。投稿に失敗しても公開は巻き戻らない。

必要な GitHub Secrets（リポジトリの Settings → Secrets and variables → Actions）:

```
X_API_KEY
X_API_SECRET
X_ACCESS_TOKEN
X_ACCESS_TOKEN_SECRET
```

X の開発者ポータル（https://developer.x.com/）でアプリを作り、
**Read and Write 権限**にしてから4値を発行する。Read のみだと投稿が 403 で落ちる。

投稿済みの記事は `data/xposted.json` に記録され、二重投稿を防ぐ。
このファイルは Actions が自動でコミットする。

投稿文の確認は手元でできる（認証情報は不要）:

```bash
python scripts/xpost.py --dry-run --date 2026-08-19
```

#### 画像を上げたくなったら

いまは **OAuth 1.0a**（アクセストークン無期限、更新不要）で、テキストと記事URLだけを投稿する。
画像は X が `og:image` から OG カードとして自動展開するため、アップロードしていない。

**自分で画像をアップロードするには OAuth 2.0 への移行が必要。**
v2 のメディアAPIは `Authorization: Bearer` を要求し、1.0a では通らない（2026-08 時点）。
移行には、リフレッシュトークンを実行のたびに GitHub Secret へ書き戻す仕組み
（libsodium 暗号化と、secrets 書き込み権限を持つ PAT）が要る。

手順は `scripts/xpost.py` の「認証と送信 — ここが差し替え点」に書いてある。
**着手する条件は「上げたい画像が実際にあるとき」。** 具体的には自分で撮った写真や図解。
公式サイトの製品画像を X にアップロードするのは、本サイトの画像方針
（権利者のサーバーを参照するだけで複製しない）から外れるので行わない。

**x-poster アプリとは意図的に分離している。** 認証情報を共有すると
別アカウントへ誤投稿する危険があるため（`x-poster/DESIGN.md` の事故記録を参照）。
詳しい理由は `scripts/xpost.py` の冒頭に書いてある。

### 広告表示（景品表示法・ステマ規制）

2023年10月施行の規制により、**アフィリエイトリンクを含む記事には広告である旨の明示が必要。**
サイトのどこかに書いてあるだけでは足りず、該当記事の目立つ位置に出す必要がある。

`build.py` が自動で処理する。アフィリエイトリンクが1つでもある記事は、
本文冒頭に「この記事にはアフィリエイト広告を含みます」が入り、代替品の見出しに「広告」ラベルが付く。
文言は `site.yaml` の `affiliate.disclosure` で変更できる。

**この表示を消す改修をしてはいけない。** 人間の判断に委ねると必ず漏れるため、
コード側で強制する設計にしてある。

## 5. 法務・権利の再確認

- 元記事の文章を丸ごと翻訳して載せない（翻訳権の侵害にあたりうる）
- 画像を転載しない。プレス素材でも利用条件を確認する
- 事実（スペック・価格・日付）そのものに著作権はない。**事実を抜き出して自分の言葉で書く** のが安全かつ品質も高い
- 引用する場合は、出典明示・引用部分の明確な区別・主従関係（自分の記述が主）の3点を守る
- 訂正依頼への窓口を `about.html` に用意しておく（現在「準備中」。連絡先を入れること）
